## 4. Workstream 1: Reader Claim/Evidence Evaluation Sidecar

Primary files:
- `/Users/jangseongjin/paperpipe/src/agents/reader_agent.py`
- `/Users/jangseongjin/paperpipe/src/services/citation_grounding.py`
- `/Users/jangseongjin/paperpipe/src/quality/claimset_policy.py`
- `/Users/jangseongjin/paperpipe/src/services/deepread_note_writer.py`

Why first:
- this is the highest artifact contamination risk
- reader output becomes the basis for claimset artifacts and note-facing summaries

### Goals
- quantify unsupported claim rate
- quantify evidence grounding accuracy
- measure claim compression drift
- measure limitation grounding quality

### Deliverables
- run-level reader evaluation sidecar
- aggregate metrics summary for a bounded paper set
- explicit unknown / unsupported / ambiguous taxonomy counts

### Checklist
- Define the sidecar schema and keep it additive.
- Record per-claim fields for `supported`, `unknown`, `unknown_reason`, `grounded`, `resolution`, and compression notes.
- Record aggregate run metrics for unsupported claim rate and grounding success rate.
- Keep the sidecar separate from canonical claimset output.
- Ensure the evaluation artifact can be generated by offline replay.
- Ensure the evaluation artifact can be linked back to the exact run id and paper id.
- Add a bounded regression fixture for at least one real-paper replay and one synthetic failure case.

### Suggested metrics
- `claim_count`
- `unsupported_claim_rate`
- `unknown_rate`
- `grounded_span_rate`
- `ambiguous_grounding_rate`
- `failed_grounding_rate`
- `limitation_grounded_rate`
- `compression_drift_rate`

### Acceptance criteria
- sidecar generation does not modify canonical claimset files
- replay works without changing the main runtime orchestration
- one bounded report can identify at least one concrete reader failure mode without manual log spelunking

## 5. Workstream 2: Stats Fallback Taxonomy and Parser Comparison

Primary files:
- `/Users/jangseongjin/paperpipe/src/agents/stats_agent.py`
- `/Users/jangseongjin/paperpipe/src/ingest/cloud_table_fallback.py`
- `/Users/jangseongjin/paperpipe/docs/Stats_Verification_Agent_Spec.md`

Why second:
- stats output is user-trusted by default
- the current quality bottleneck is often fallback behavior and table fidelity, not only model reasoning

### Goals
- measure how often `unverifiable` is caused by parser issues vs real missing evidence
- measure degenerate-table fallback frequency
- compare local parser output and cloud fallback recovery rate

### Deliverables
- stats fallback taxonomy artifact per run
- parser-vs-cloud comparison summary for a bounded sample
- explicit count of recovered useful tables

### Checklist
- Emit a stable fallback reason field for every stats run.
- Distinguish `no_table`, `degenerate_table_shape`, execution failure, and unsupported claim input.
- Log whether cloud fallback was invoked and whether it improved usable table coverage.
- Record execution success vs fallback short-circuit rates.
- Keep parser comparison bounded to a small, curated sample.
- Preserve current short-circuit behavior for degenerate tables.
- Do not change parser/provider selection policy in this phase.

### Suggested metrics
- `stats_execution_success_rate`
- `unverifiable_rate`
- `degenerate_table_rate`
- `cloud_fallback_invocation_rate`
- `cloud_recovery_useful_table_rate`
- `parser_vs_cloud_delta`
- `false_verified_count`
- `false_inconsistent_count`

### Acceptance criteria
- every stats artifact run can be assigned to a bounded fallback bucket
- one comparison report can show whether parser fidelity or model reasoning is the bigger current bottleneck
- no change to the existing deterministic fallback semantics is required to collect the data

## 6. Workstream 3: Teacher Review Spot-Check Protocol

Primary files:
- `/Users/jangseongjin/paperpipe/src/quality/teacher_review.py`
- `/Users/jangseongjin/paperpipe/src/quality/claimset_policy.py`

Why next:
- teacher review is not the first user-facing risk, but it can silently distort the quality loop

### Goals
- measure agreement between teacher review output and manual spot-checks
- identify whether supported-claim filtering is precise enough for future benchmark use

### Deliverables
- spot-check checklist
- review agreement summary for a bounded bundle sample
- documented escalation rule for `no_supported_claims` and mixed-quality outputs

### Checklist
- Define a small sample size for manual spot-checking.
- Record whether each reviewed claim is truly supported, unsupported, or ambiguous.
- Record whether location augmentation improved or degraded inspectability.
- Log `no_supported_claims` frequency separately.
- Keep the protocol light enough to run repeatedly.
- Store spot-check outcomes outside the canonical teacher output artifact.

### Suggested metrics
- `review_agreement_rate`
- `supported_claim_precision`
- `no_supported_claims_rate`
- `location_augmentation_hit_rate`
- `manual_override_rate`

### Acceptance criteria
- spot-check results can be compared against teacher output without editing the original artifact
- at least one recurring disagreement pattern is surfaced or the protocol can justify that it is not currently a major risk

## 8. Workstream 5: Cloud Table Fallback Cost/Fidelity Review

Primary files:
- `/Users/jangseongjin/paperpipe/src/ingest/cloud_table_fallback.py`

Why last:
- it is an optional, bounded fallback path
- cost and benefit should be measured before changing policy

### Goals
- understand whether the cloud fallback recovers enough useful tables to justify its usage

### Deliverables
- bounded cost/fidelity report
- recommendation on whether to keep current fallback thresholds unchanged

### Checklist
- Count invocation frequency over a bounded sample.
- Count accepted recovered tables.
- Count cases where fallback did not improve stats inspectability.
- Record estimated cost per useful recovered table.
- Keep the report separate from runtime policy changes.

### Suggested metrics
- `fallback_invocation_rate`
- `accepted_table_rate`
- `useful_recovery_rate`
- `cost_per_useful_table`

### Acceptance criteria
- the team can justify keeping or tightening the fallback path with evidence rather than intuition

## 9. Sequencing Rules

Use this order:
1. Reader evaluation sidecar
2. Stats fallback taxonomy
3. Teacher review spot-check protocol
4. Processor and watcher override logging
5. Cloud fallback cost/fidelity review

Do not reorder the sequence unless a new production incident shows that intake classification is causing more damage than claim or stats artifacts.

## 10. Decision Gates Before Any Training

All of these should be true before proposing fine-tuning or broader model changes:
- reader sidecar metrics exist for a bounded real-paper sample
- stats fallback metrics exist for a bounded real-paper sample
- teacher review spot-check results exist
- at least one repeated failure mode is measurable at field level
- offline replay is available for the target lane
- the improvement target cannot be addressed more cheaply with guardrails, verifier logic, or logging

If any item above is missing, the default decision is:
- evaluation and logging first
