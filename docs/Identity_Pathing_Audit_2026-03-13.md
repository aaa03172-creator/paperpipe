# Identity And Pathing Audit

Status: Working infrastructure audit  
Date: 2026-03-13  
Scope: `paper_id`, `doc_id`, `job_id`, `run_id`, `chunk_id`, artifact paths, and related DB/path contracts

## 0. Executive Summary

The current runtime is operational, but the identity/pathing layer is still transitional.

The main shape of the problem:

1. `paper_id` is being used as both a logical identity and a filesystem path segment
2. `doc_id` exists as a parallel identity in artifacts/agents
3. `job_id` and `run_id` are generated by multiple schemes
4. `chunk_id` is not deterministic in the active indexing lane
5. there is no global identity helper layer (`paper_key`, alias map, DOI normalization contract)

Current judgment:

- execution is stable enough to build on
- identity/pathing is not yet standardized enough for memory-ready hooks or durable evidence contracts

## 1. Current Identity Layers

### 1.1 `paper_id`

Observed usage:

- DB primary key in `papers`
- queue key for job enqueue/dedup
- artifact path segment under `storage/artifacts/{paper_id}/{run_id}`
- paper notes API key
- export/note-generation lookup key
- backfill/ops/reporting key

Primary evidence:

- `/Users/jangseongjin/paperpipe/scripts/init_db.py`
- `/Users/jangseongjin/paperpipe/src/db_utils.py`
- `/Users/jangseongjin/paperpipe/src/jobs/queue.py`

- `/Users/jangseongjin/paperpipe/backend/main.py`
- `/Users/jangseongjin/paperpipe/backend/routers/obsidian.py`

Current reality:

- there is no single helper that defines how `paper_id` should be created
- comments imply priority order such as DOI/PMID/hash, but no canonical implementation was found
- some local DOI normalization exists inside parser code, but not as a project-wide identity contract

Assessment:

- `paper_id` behaves like a canonical key in practice
- it is not actually governed by a canonical factory

### 1.2 `doc_id`

Observed usage:

- root identity for `DocumentArtifact`, `IndexArtifact`, and `ClaimSet`
- examples include `doi:...`, `pmid:...`, `file:...`
- deepread agents mostly talk in `doc_id`, while queue/runtime orchestration mostly talks in `paper_id`

Primary evidence:

- `/Users/jangseongjin/paperpipe/src/schemas/agent_artifacts.py`
- `/Users/jangseongjin/paperpipe/src/agents/reader_agent.py`
- `/Users/jangseongjin/paperpipe/src/agents/ingest_agent.py`

Current reality:

- `doc_id` and `paper_id` are often close, but they are not explicitly mapped
- in some paths they may coincide (`doi:...`)
- in others they may diverge (`file:...` ingest fallback, legacy rows, note-driven flows)

Assessment:

- `doc_id` is the artifact/agent identity
- `paper_id` is the runtime/storage identity
- there is no formal bridge between the two

### 1.3 `job_id`

### 1.5 `chunk_id`

Assessment:

- this blocks a robust evidence resolver design

## 2. Current Pathing Contracts

### 2.1 Runtime path contract

Verified current rule in `/Users/jangseongjin/paperpipe/src/services/runtime_paths.py`:

1. if `PAPERPIPE_STORAGE_DIR` is set, use it
2. else if `PAPERPIPE_HOME` is set, use `<home>/storage`
3. else default to the current workspace `storage/`

Affected helpers:

- `state_db_path()`
- `artifacts_root()`
- `meeting_packs_root()`
- `search_eval_root()`
- `profiles_config_path()`
- `config_file_path()`

Assessment:

- this runtime contract is now internally consistent
- it is good enough as the current base path rule

### 2.2 Artifact path contract

Observed path:

- `storage/artifacts/{paper_id}/{run_id}`

Primary evidence:

- `/Users/jangseongjin/paperpipe/backend/services/job_runner.py`
- `/Users/jangseongjin/paperpipe/backend/main.py`
- `/Users/jangseongjin/paperpipe/backend/routers/obsidian.py`
- `/Users/jangseongjin/paperpipe/src/services/paper_ops_summary.py`

Current reality:

- raw `paper_id` is used directly as a directory name
- no `paper_key` indirection exists
- APIs and ops summaries assume the same raw path contract

Assessment:

- this works today
- it is not safe as a long-term canonical storage contract because `paper_id` can contain `:` and `/`

### 2.3 Note/export path contract

Observed path:

- exporter sanitizes note filenames via `_expected_obsidian_relpath_for_paper_id()`

Primary evidence:

- `/Users/jangseongjin/paperpipe/src/exporter.py`

Current reality:

- note filenames are sanitized to alnum/space/hyphen/underscore
- artifact directories are not similarly sanitized

Assessment:

- note pathing and artifact pathing already use different identity-to-path transforms
- this split is one of the clearest signs that `paper_id` is overloaded

## 4. Confirmed Gaps

### P0

1. No canonical `paper_id` factory
- there is no shared helper equivalent to `make_paper_id()`
- comments and implementation are not the same thing

2. Raw `paper_id` is used directly in artifact paths
- current path contract is filesystem-fragile for DOI-style ids with `/`

3. `chunk_id` is not deterministic in the active indexing path
- `uuid4()` chunk ids prevent stable evidence contracts

### P1

4. `paper_id` and `doc_id` are parallel identities without a formal bridge
- current code relies on convention, not contract

5. `run_id` generation is inconsistent across queue, job runner, skills, and eval tooling
- no shared temporal/stable scheme exists

6. DB has no alias/mapping layer for identity migration
- future move from raw `paper_id` to `paper_key` would require careful migration

### P2

7. `artifact_dir` is stored as a concrete path, not just derived from ids
- helpful today, but increases drift risk when path contracts change

8. note path sanitization and artifact pathing already disagree
- this is currently survivable, but it signals technical debt

## 5. What Is Good Enough Today

The following can be treated as acceptable current baseline:

- runtime base paths now resolve consistently
- `paper_id` works well enough as the DB/runtime lookup key
- current APIs can find latest runs and artifacts
- Meeting Pack and Obsidian surfaces use the same artifact root contract

This means identity/pathing is not blocking day-to-day runtime operation.

## 6. What Must Happen Before Memory-Ready Hooks

Recommended migration order:

1. add canonical identity helpers
- `normalize_doi()`
- `make_paper_id()`
- `make_paper_key()`
- `new_run_id()` / `new_job_id()`

2. separate logical ids from path keys
- keep `paper_id` as logical identity
- add `paper_key` for filesystem-safe pathing

3. standardize execution ids
- one project-wide `run_id` format
- one project-wide `job_id` format

4. make chunk identity deterministic
- stable `chunk_id` from parser/chunker/config tuple

5. only then add memory/event-log hooks
- otherwise event linking will be built on unstable references
