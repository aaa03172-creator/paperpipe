사례 1-1. 좋은 서론(Introduction)의 4단 구조
출처: KakaoTalk_Photo_2026-01-21-18-17-33 001 (Threads 캡처)
핵심 내용
1) ‘지금 세상이 마주한 문제’를 제시한다.
2) ‘기존 연구들이 어떻게 설명해왔는지’를 요약한다.
3) ‘하지만 아직 남아 있는 결정적 질문’을 한 문장으로 뽑는다. (서론의 핵심)
4) ‘이 연구는 그 질문을 다룬다’로 연결한다.
참고/적용 포인트
PaperPipe 노트 템플릿(Obsidian)에서 ‘서론/배경 → Gap → 내가 읽어야 하는 이유’ 구조로 그대로 재사용 가능.
Triage reason(선정 이유) 문장을 ‘3) 결정적 질문’ 형태로 만들면, 나중에 다시 봐도 가치 판단이 빠름.

사례 1-2. Research Question(RQ) 만들기: 관찰 → 의문 유도
출처: KakaoTalk_Photo_2026-01-21-18-17-33 004 (Threads 캡처)
핵심 내용
먼저 현상을 관찰하게 하고, 그 다음 ‘의문’을 던지도록 유도한다.
질문은 ‘아주 쉽게’ 시작한다(무엇이 변하는지/무엇이 궁금한지).
RQ는 탐구적이며, 아직 결론이 나지 않은 상태여야 한다.
예시: ‘북성로의 적산가옥을 리모델링해 카페/갤러리로 만들면 지역이 활성화될까?’
참고/적용 포인트
Slot 정의를 ‘질문(가설) 형태’로 한 줄로 적어두면, LLM 판정 기준(근거/스니펫) 작성이 쉬워짐.
Triaging에서 ‘이 논문이 어떤 질문에 답하는가?’를 1줄로 남기는 규칙을 추가하면 검색/회고가 좋아짐.

사례 1-3. 선행연구 고찰은 ‘요약’이 아니라 ‘내 관점/한계’가 보여야 한다
출처: KakaoTalk_Photo_2026-01-20-21-53-02 018 (Threads 캡처)
핵심 내용
피드백 요지: ‘논문은 읽었지만, 너의 생각이 보이지 않는다’는 지적이 자주 나온다.
개선 포인트: 논문을 단순 요약으로 끝내지 말고, 마지막 문장에 (1) 분류(타입)와 (2) 한계/시사점을 붙인다.
즉, ‘A는 B로 설명한다’에서 끝내지 말고 ‘하지만 C가 부족/제한적’까지 써야 한다.
참고/적용 포인트
PaperPipe 노트에 ‘1줄 요약 + 1줄 한계(또는 내가 보는 gap)’ 필드를 추가하면, 후속 연구 질문 도출에 도움.
Agent가 생성하는 triage_reason에 ‘왜 중요한가/무엇이 비었나’를 1문장만 더 붙이는 옵션을 고려.
2. 논문 읽기·정리·도구 활용 사례

사례 2-1. Windows 스케줄러로 ‘매일 최신 논문 → Obsidian 자동 저장’ 구축
출처: KakaoTalk_Photo_2026-01-20-21-53-01 011 (Threads 캡처)
핵심 내용
Task Scheduler로 스크립트를 주기 실행해, 여러 저널/소스에서 최신 논문을 수집해 Obsidian에 저장.
LLM(Gemini 등)로 요약/정리를 붙이는 방식이 언급됨.
자동화는 편하지만, 최종 선별은 사람(휴먼 체커)이 필요하다는 문제도 함께 언급됨.
참고/적용 포인트
PaperPipe의 ‘Trigger(30~60분) + 오늘 실행 기록’ 정책과 유사한 운영 사례.
요약/태깅은 자동화하되, ‘needs_review/low_confidence’로 사람 검토 루프를 남기는 접근이 현실적.

사례 2-2. Obsidian + Antigravity로 ‘연구 계획(.md) → 관련 논문 탐색/저장’ 워크플로우
출처: KakaoTalk_Photo_2026-01-20-21-53-01 012 (Threads 캡처)
핵심 내용
연구 계획을 Markdown으로 정리해 두고, 그 내용을 기반으로 관련 논문을 찾아 저장하는 흐름.
키워드 가중치/스코어링 기반 스크리닝, 변수 조합으로 연구 아이디어 생성, 네트워크 시각화 등의 아이디어가 언급됨.
Obsidian을 ‘연구 자산 저장소’로 두고 에이전트가 그 위에서 움직이는 형태.
참고/적용 포인트
PaperPipe의 ‘config 기반 Slot/Query’와 궁합이 좋음: 계획(.md) → config.yaml로 반영 → 자동 수집/선정.
‘연구 계획 → 관련 논문군’의 연결 고리를 유지하려면, 노트/CSV에 ‘project_id’ 같은 컨텍스트 컬럼을 추가하는 것도 방법.

사례 2-3. Obsidian 볼트 구조화: 번호/역할 기반 파일 체계 + AI 정리 파일(GEMINI.md)
출처: KakaoTalk_Photo_2026-01-20-21-53-01 013 (Threads 캡처)
핵심 내용
노트/파일을 역할별(예: Index, Input, Output 등)로 나누고 번호를 붙여 흐름을 관리하는 사례.
AI에게 정리/구조화를 요청하기 위한 전용 지시 파일(예: GEMINI.md)을 두는 방식이 언급됨.
노트 이동/승격(임시→정리본) 같은 ‘상태 전이’ 개념을 활용.
참고/적용 포인트
PaperPipe에도 ‘status/state(예: inbox→skim→deep)’를 일관된 규칙으로 두면 관리가 쉬움.
에이전트 지시를 모아두는 파일(AGENT_RULES.md 등)을 repo 루트에 두는 것도 도움이 됨.

사례 2-4. Zotero 운영 팁: 폴더/싱크/파일 이동 자동화(zotmoov 등) + Obsidian 연계
출처: KakaoTalk_Photo_2026-01-20-21-53-02 014 (Threads 캡처)
핵심 내용
Zotero는 로컬 폴더 기반으로 자료를 관리하고, 필요시 동기화(유료/무료 조합)를 선택할 수 있다는 흐름.
PDF/첨부 파일을 원하는 폴더로 정리해 주는 도구(zotmoov)와 클라우드(iCloud 등) 연계 사례가 언급됨.
Obsidian 플러그인으로 Zotero 노트/메타데이터를 끌어오는 연계 아이디어가 언급됨.
참고/적용 포인트
PaperPipe의 ‘Zotero DB 직접 write 금지 + .ris export’ 정책과 잘 맞는 현실적 운영 레퍼런스.
PDF 저장 위치 규칙(attachments_dir)과 Obsidian 링크 규칙을 config로 고정하면 유지보수성이 좋아짐.

사례 2-5. PDF에 직접 주석/요약을 넣는 파이썬 도구 아이디어(AnnotateAI)
출처: KakaoTalk_Photo_2026-01-20-21-53-02 015~016 (Threads 캡처)
핵심 내용
PDF에서 핵심 개념을 추출하고, 중요한 문단을 찾아 요약/하이라이트/메모를 PDF에 직접 남기는 접근이 소개됨.
의학/과학 논문 읽기 시간을 줄이는 용도에 초점을 둔 것으로 보임(설명 기반).
‘최적의 문단 추천 → 요약 → 주석’의 파이프라인 형태.
참고/적용 포인트
PaperPipe 3단계(고도화)에서 ‘정독 후보 3편’에만 적용하는 옵션으로 고려 가능(전 논문에 적용하면 비용/시간 부담).
MVP에서는 ‘pdf_missing/노트 요약’까지만 하고, 주석은 선택 기능으로 분리하는 것이 안전.

사례 2-6. 논문 읽기 실전 팁: 레퍼런스 추적, 핵심 Figure 중심, Supplement 처리
출처: KakaoTalk_Photo_2026-01-20-21-53-02 017 (Threads 캡처)
핵심 내용
관련 레퍼런스를 타고 들어가며 맥락을 확장한다.
논문의 ‘메인 Figure’를 중심으로 논리 흐름을 잡는다.
Supplementary 자료는 필요한 부분만 잘라서 관리/리뷰한다.
저널 미팅용 PPT처럼 ‘핵심만 재구성’해보는 연습이 도움된다는 취지.
참고/적용 포인트
PaperPipe 노트 템플릿에 ‘Key Figures / Claim–Evidence’ 섹션을 두면, deep read의 산출물이 표준화됨.
Supplement 링크/파일명 규칙을 정해두면(예: PMID_supp1.pdf), Watch Folder 매칭에도 유리.

사례 2-7. 여러 프로젝트의 논문을 Obsidian에서 관리하는 방식: 프로젝트 폴더 + 1줄 요약 + 상태표
출처: KakaoTalk_Photo_2026-01-20-21-53-02 019~020 (Threads 캡처)
핵심 내용
프로젝트별 폴더를 만들고, 하위에 주제/카테고리로 분류한다.
각 논문은 ‘한 문장 요약(키워드 + 링크)’을 남겨 빠르게 회고할 수 있게 한다.
읽음/안읽음/중요도 등을 표(테이블)로 관리해 리딩 진행도를 트래킹한다.
참고/적용 포인트
PaperPipe의 paper_collection.csv를 ‘프로젝트/상태/우선순위’까지 관리하는 중심 장부로 두는 운영 사례로 참고 가능.
Obsidian 노트에도 ‘one-liner + status + next_action’ 필드를 고정하면 회고와 재진입이 쉬움.
3. 에이전트·코딩 워크플로우 사례

사례 3-1. 단일 에이전트 vs 병렬/다중 에이전트: 언제 무엇이 유리한가
출처: KakaoTalk_Photo_2026-01-21-18-17-33 002 (Threads 캡처)
핵심 내용
단일 에이전트 장점: 설정이 간단, 오버헤드 적음, 디버깅/추적이 쉬움.
단일 에이전트 한계: 대규모 프로젝트에서 컨텍스트 과부하, 느린 반복 작업, 단일 장애 지점.
다중 에이전트 장점: 처리량 향상, 복잡한 의존성 처리, 도메인별 전문가 분업.
다중 에이전트 한계: 조정 오버헤드, 충돌 가능성, 공유 메모리(예: 벡터DB) 필요.
팁: 초기에는 2~3명 수준으로 제한하고, 명확한 경계를 설정(도구 공유는 MCP 등 활용).
참고/적용 포인트
PaperPipe MVP는 단일 에이전트/단일 파이프라인으로 시작하는 게 유리(디버깅/재현성).
고도화(3단계)에서 ‘수집/분류/추출/내보내기’가 커지면 역할 분리(서브에이전트/스킬)로 확장.

사례 3-2. Antigravity Skills 사용법 요약: 폴더 위치, SKILL.md, 스킬 호출
출처: KakaoTalk_Photo_2026-01-21-18-17-33 003 (Threads 캡처)
핵심 내용
스킬 폴더 위치: (프로젝트 전용) {프로젝트 루트}/.agent/skills/my-skill/ 또는 (글로벌) ~/.gemini/antigravity/skills/my-skill/ 형태로 구성.
SKILL.md 상단에 YAML Frontmatter로 ‘언제/어떻게 이 스킬을 쓸지’ 메타데이터를 적는다.
에이전트에게 특정 스킬을 쓰게 하고 싶으면 스킬 이름을 직접 언급해 호출한다.
참고/적용 포인트
PaperPipe에서는 ‘pubmed_search’, ‘unpaywall_fetch’, ‘ris_export’, ‘obsidian_note’ 같은 반복 작업을 스킬로 분리하면 명확해짐.
스킬 메타데이터에 ‘입력/출력 스키마’를 적어두면 LLM 오작동이 줄어듦.

사례 3-3. Claude/에이전트 설정 팁: Skills·Hooks·Subagents 역할 분리 + 규칙 자동 감사
출처: KakaoTalk_Photo_2026-01-21-18-17-34 005 (Threads 캡처)
핵심 내용
역할 분리: Skills(한 줄 커맨드로 워크플로우 실행), Hooks(Pre/Post/Stop 시점 자동화), Subagents(planner/architect/tdd/security 등).
규칙 모듈화: 보안/코딩스타일/테스트/성능 규칙을 파일로 분리해 일관성 있게 적용(예: ‘console.log 금지’ 같은 규칙을 Stop Hook에서 자동 검사).
실전 팁: 로컬+웹 통합 검색(mgrep), Git Worktrees로 기능별 독립 작업/병렬 개발, Zed 에디터의 실시간 추적 등.
추가 원칙: 안 쓰는 MCP/플러그인을 줄여 컨텍스트 여유 확보, 반복은 Hooks로 제거, 서브에이전트 스코프는 좁게.
참고/적용 포인트
PaperPipe에 ‘pre-commit(포맷/타입체크)’, ‘Stop Hook(테스트 필수)’ 같은 개발 규칙을 문서/스크립트로 고정하면 품질이 안정됨.
Ticket 단위 개발 원칙과 결이 같아서, 에이전트 운영 규칙(Rules) 섹션 보강에 참고 가능.

사례 3-4. Chain-of-Code 팁: ‘수도코드(로직) → 코드’ 순서로 요청하면 버그가 줄어든다

핵심 내용
데이터베이스에서 ‘랜덤 번호’로 저장된 PDF 파일을 일일이 폴더에 정리하고, 노트와 매칭하는 작업이 가장 번거로운 병목이었다.
해결: 기존에 다운로드해 둔 PDF를 Obsidian의 Recent(또는 특정 폴더)에 그대로 두고, Antigravity에게 파일명을 미리 정한 스키마로 일괄 변경하도록 요청한다.
그 다음 Antigravity가 PDF를 하나씩 읽고, 지정한 노트 스키마(섹션 구조)에 맞춰 요약/노트정리 및 태깅까지 수행한다.
APA 스타일의 서지정보(제목/저자/저널 등)를 함께 채워 달라고 하면, 웹에서 메타데이터를 찾아 노트에 보강할 수 있다.
임팩트 논문(핵심 근간 논문)들을 함께 넣어두고 같은 방식으로 정리하면, 논문 간 ‘이론적 연결’을 개인용 Connected Papers처럼 구축할 수 있다는 아이디어다.
결과적으로 RA성 반복 업무(정리·매칭·태깅)가 자동화되어, 연구 노트 관리의 품질과 속도를 동시에 올릴 수 있다.
PaperPipe에 참고할 적용 포인트
Watch Folder를 ‘신규 수집 PDF’뿐 아니라 ‘기존 보유 PDF(Recent/Archive)’까지 확장하는 옵션을 두면, 과거 자산 정리도 파이프라인에 포함할 수 있다.
File Renamer(스키마 강제) 모듈을 명시: (DOI/PMID 기반) 파일명 통일 + 충돌 시 suffix/버전 처리로 안전하게 리네이밍.
서지정보 보강 단계: PubMed/Crossref 등에서 서지 메타데이터를 가져와 APA/CSL에 필요한 필드(저자, 연도, 저널, 권/호, 페이지, DOI, URL)를 채우는 ‘enrich’ 스텝을 분리.
‘Core/Impact papers’ 컬렉션을 별도로 운영하고, 신규 논문과의 연결(키워드/임베딩/인용 네트워크)을 산출물에 포함하면 “이론적 근간 연결”이 자동화된다.
Antigravity 스킬/커맨드 관점에서는: “폴더의 PDF → 스키마 리네임 → 노트 생성 → 태깅/서지 보강”을 1줄 명령으로 캡슐화하면 재사용성이 높다.
